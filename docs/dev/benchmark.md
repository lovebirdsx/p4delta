# 性能测量与 dry run 比对

## 预览性能测量（PowerShell 7）

`scripts/benchmark.ps1` 固定执行预览（`-l`，不传 `-a`），先预热一次，再计时 5 轮：

```powershell
cargo build --release --locked
pwsh -File scripts/benchmark.ps1 -Binary ./target/release/p4delta.exe `
    -Workspace <client> -Path <本地目录> -OutDir <扫描范围外的新输出目录>
# 可选：-Mode clean，或 -Mode sync -To <CL> -VerifyAll
# 剪枝对照：相同场景另跑一份 -NoPruneIgnoredDirs
pwsh -File scripts/test-benchmark.ps1
```

每次输出到新目录，保留原始 stdout/stderr 与 `result.json`；预热与计时轮的动作和完整路径按区分
大小写的多重集比较，乱序不算差异，重复数量参与比较。输出目录与测量目录不得互相包含，避免
基准日志污染扫描。遇到转交原生 P4 的不支持文件时，因清单不完整而拒绝报告成功的基准结果。
对照不同构建或剪枝开关时，先核对动作一致，再比较多轮耗时，不能只比最快的一轮。

脚本不清除摘要缓存，也不控制操作系统文件缓存；正常档是自然预热后的重复测量，`-VerifyAll`
仍每轮绕过摘要缓存与时间戳捷径，不是“冷操作系统缓存”测量。峰值工作集只覆盖主进程，
不包含 P4 子进程；退出后无法取得有效峰值时，使用运行期间每 50 ms 刷新采样所得的下界，
始终取不到有效值则记 `null`。目前没有分阶段耗时、服务端负载或进程树峰值统计，也不在 CI
里设耗时硬阈值。脚本测试使用假 CLI 与模拟进程对象，不访问真实 P4。

## 用 dry run 日志比对行为

判断改动是否影响 dry run（`-l`）的输出时，**不要直接逐行 diff**，按三层来：

1. **先剥离 `^... ` 开头的字段行做多重集比对**：`tr -d '\r' | grep '^\.\.\. ' | LC_ALL=C sort | md5sum`。这一组行的 md5 相同 = p4 返回的数据完全一致。行序会因并发而变（fstat 由多个子进程各写各的），所以先排序。
2. **再看非 `...` 的结构性输出行**（`grep -v '^\.\.\. '`）：顺序稳定，可以逐行 diff，只允许计时行不同。
3. **计时行归一化**：`sed 's/[0-9.]* seconds/<T> seconds/'` 之后再比。

两个会得出错误结论的陷阱：

- **PowerShell 里 `git diff --no-index a b 2>$null` 会静默失败**：不输出任何内容、看起来像「零差异」，实际是命令没跑成。别用它下「逐字节一致」的结论，改用 `diff`、`Get-FileHash` 或 `fc`。
- **重定向方式会改变字节数**：Rust 的 `println!` 只输出 `\n`，但 PowerShell 的 `>` 会转成 `\r\n`，Git Bash 的 `>` 又会把 `\r` 吃掉。不同 shell 捕获的输出直接比 `wc -c` 必然不等；比内容前先 `tr -d '\r'`，或者两次用同一种方式捕获。

验证 CLI 表面（`--help` / `--version`）时同理：从基线 worktree 重新构建原始二进制，用同一种 shell 分别捕获两者再比 md5。

## 真实工作区上的端到端验证

真实大工作区上的 A/B 跑过一轮（客户端的两个真实子目录：一个 589 文件，一个 44,554 文件 5.09 GiB）：前者原生 10 个 `updating`、我们 10 个 `Update`，文件集合逐条相同。`--to <CL>` 换成一个能真正区分 head 与目标的目标 CL 后（某文件在那里是 `#34`、head 已是 `#35`），两边仍是同样的那 10 个文件。后者整轮 dry run 2.54 s（摘要缓存全命中）。**那里出现过一次分歧**：原生打了 22 行 `deleted as` 而我们说「无事可做」——逐条核实后那 22 个既不在磁盘上也没有 have 记录，原生那几行只是描述目标状态、p4 自己也无事可做，结论钉在 `a_deleted_target_with_nothing_local_is_a_no_op` 里。

这一轮是**一次性的人工核对**，没做成自动化（要连真实的 P4 工作区，CI 上跑不了），而且全程 dry run——`-a` 会动到那份真实工作区。所以它验证的是「取数、分类、集合」三者与原生一致；**「钉住的确实是目标那一版（`#34` 而非 `#35`）」只有沙箱用例有独立取证**（`p4 fstat` 读回的 `haveRev`），工具自己的输出里不打印目标版本号。

在真实工作区上做端到端验证，有几条实测出来的做法：

- **按规模分级挑测试目录，从最小的开始**：整棵工作区可能有上千万个 depot 文件，不能对整棵树跑 reconcile。挑几个文件数跨度大的真实子目录（几百 / 几千 / 几万 / 几十万），逐级往上跑，确认无误再换下一级——`p4 reconcile -n` 在 4 万多文件上就要一百秒左右，再往上超线性增长。
- **只读子树不能当探针**：权限不足的目录里 `p4 edit` 会报 `no permission for operation on file(s).`，而 p4 的退出码仍是 0——用 `-a` 验证「变更真的应用了」时拿它当探针，会得出错误的结论。
- **最小探针目录**：挑一个只有一两个已同步文件的目录，改一行跑 `-a -l`，就能验证「文件真的进了 default changelist」，收尾用 `p4 revert`。
- **先 `cd` 进工作区再手工跑 p4 对照**：p4 从 cwd 往上找 `.p4config`，而工具会把子进程的 cwd 设成被处理的工作区目录。工作区里那份 `.p4config` 覆盖注册表配置（例如 `P4IGNORE`）时，站在仓库目录里手工跑的 p4 用的是另一套规则——不切 cwd 就对照，会得出「工具行为不一致」的假结论。
- **`-v` 的输出行序不确定**：fstat 由多个 p4 子进程并发跑，各自把原始行回显到 stdout，交错顺序取决于调度——同一个二进制连跑两次，输出可能一次与基线逐行一致、一次整段乱序。**不要逐行 diff `-v` 输出**，先剥离 `^... ` 字段行做多重集比对，方法见「用 dry run 日志比对行为」。
- **全程 dry run 是安全的**：`-l`（不加 `-a`）与 `p4 reconcile -n` 都不改动任何东西；验证后用 `p4 opened` 确认测试目录下没有文件被打开。

真实工作区里**碰不到 archive / p4 将来才引入的未知文件类型**：几十万个真实文件里 `headAction` 只出现过 add/branch/delete/edit/integrate，`headType` 只出现过现有的几个基础类型。这类「不中止整轮」的路径只能靠单元测试覆盖，不必花时间在真实环境里找样本。
